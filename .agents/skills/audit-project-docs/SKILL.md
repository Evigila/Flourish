# Audit SAF structure

1. Resolve the root. Read `AGENTS.md`, `SAF.lock.json`, and the audit gate/required structure in [rules.md](../../../docs-ai/common/rules.md). Read `SAF.json` for the effective version. Resolve project-owned `SAF.config.json` through `Resolve-SafConfig -Root <root>` in `scripts/saf-core.ps1`, applying configured protections/verification restrictions without expanding authorization. Follow the fixed monthly gate; if it returns `SKIP_AUDIT` and no SAF structure audit was requested, continue the original task. This is an Agent skill, not a `local.bat` command.
2. Check only SAF framework artifacts and required file/folder structure: required paths exist with correct types, release/config/state JSON uses supported formats, instruction/skill files are readable and structurally valid, and required Markdown documents exist in a valid format. Config is seed-only project data, not a managed hash baseline; the default consumer seed contains only the supported schema version and must not import source preferences. Unsupported schema or removed fields require explicit user migration, not silent removal/overwrite. Distinguish `.agents/skills/` from runtime `.agents/backup/`, `.agents/saf_log/`, and `.agents/operation.lock`. Empty directory markers are valid. Source bootstrap/installation may be null; do not invent installation evidence or import its audit into consumers.
3. Existing architecture/dependency seed documents satisfy the structural requirement when present and format-valid, even while their project facts remain unverified. Do not enumerate business source trees, inspect business implementation, resolve application dependencies, or require architecture/dependency facts to be populated or verified to complete this audit. Any separately requested project-content work keeps its own scope and verification status.
4. Repair authorized structural gaps from available SAF material. Create or repair AI structural documentation in English, preserving existing project content, human documentation, and history. Ask once only for genuinely unavailable material needed for the SAF structure check; missing business facts are not such a gap. Record durable structural repairs when needed.
5. Leave completion unchanged while required SAF structural checks or repairs remain unresolved. Otherwise create an audit object with effective `auditedFrameworkVersion`, actual UTC `lastCompletedAtUtc`, and preserved/applicable `lastMissingMaterialAskedAtUtc`. Dot-source `<root>/scripts/saf-core.ps1` and call `Set-SafState -Root <root> -Section audit -Value <audit-object>`. This merges only audit under the shared operation lock. Never directly rewrite the full lock or overwrite bootstrap/installation. A missing/incompatible helper is unresolved, not permission to bypass coordination.
6. Report the SAF structure inspected, structural repairs, actual checks, and unresolved structural gaps; return to the original task. Explicitly distinguish structure compliance from unverified project facts. Completion does not establish business-code correctness, architecture/dependency accuracy, or functional test success.

Use shared standards as authority without duplicating policy. Perform the required structural checks and any appropriate tests for in-scope implementation repairs, subject to explicit user limits; partial checks must not refresh completion. Do not install inspection dependencies or expand into business-code review. New commits require prior approval or existing explicit authorization; never delete or rewrite existing commits.
